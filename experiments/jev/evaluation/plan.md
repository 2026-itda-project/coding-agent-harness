# Jev 도입 검증 계획 — 사용자 검수안

상태: 대표 판정 경계 사용자 동의 완료. 전체 라벨의 독립 검수·수치 성공 기준·실행 설정은 미확정. 이 문서 준비 중 API 호출·추가 과금 없음. 이 문서는 실험 조건의 제안이며 공식 제품 정책이나 Jev 도입 확정이 아니다.

## 무엇을 증명할 것인가

1. 기존 M1 → M2 Sonnet 단독: AI 기본값과 최소 질문 정책이 질문 부담을 줄이면서 사용자 의도를 보존하는가?
2. M2 Sonnet 단독 → M2 Jev 판정: 같은 정책에서 판정 품질을 유지하며 비용·지연·불필요한 질문을 줄이는가?
3. M2 Jev + Sonnet 재검토: 재검토 비용까지 포함해 실제 흐름에서도 추가 이익이 남는가?

1번의 정책 개선 효과를 2번의 Jev 효과로 보고하지 않는다. Jev에 불리한 결과도 그대로 보고하고, 이점이 없으면 도입 보류가 정상적인 결론이다.

## 정답 경계 제안

판정 대상 한 항목에 대해 전체 사용자 발화를 읽는다. 다른 요구사항이 충분하지 않다는 이유로 이미 충분한 항목까지 ask_user로 바꾸지 않는다.

- ready: 대상 제품 의도가 명시됐거나 맥락으로 해소됐다. 명시적 예외는 일반 규칙과 함께 해석한다.
- ai_refine: 동작하는 데모에 필요한 사소한 제품 동작·안내·시연 데이터가 빠졌고 관례로 보완할 수 있다. 예: 빈 제목 저장 거절, 저장 완료 안내, 초기 예시 데이터.
- defer_to_spec: 무엇을 할지는 정해졌고 어떻게 구현·표현할지만 남았다. 예: 일반 목록 정렬, 페이지 크기, 색상·컴포넌트·DB 구조. 선착순 배정처럼 사용자 결과를 바꾸는 업무 순서는 포함하지 않는다.
- ask_user: 서비스의 중심 목적·핵심 흐름이 없거나, 명시 요구가 양립할 수 없거나, 실제 외부 연동 요구가 지원 범위와 충돌한다. 제한만 있는 기능은 무엇이 불가능한지 설명하고 데모 대안을 확인하는 질문이다. 지원 여부 자체를 사용자에게 다시 결정시키는 질문은 아니다.

모든 누락을 ask_user로 보지 않는다. 작은 충돌도 사용자 명시사항을 임의로 덮어쓸 수 없어 확인하는 안이지만, 이 부분은 사용자 검수 항목이다. 3라운드 뒤 AI 제안으로 넘어가는 정책은 전체 흐름 실험에만 적용한다. 첫 판정 실험에서 원래 정답을 ai_refine으로 미리 바꾸지 않는다.

## 120개 재검수 결과

원본 `../cases.json`은 보존한다. 수정안은 `cases.proposed.json`, 전체 읽기용은 `cases-review.md`, 변경 기록·소규모 선택 목록·파일 해시는 `review-manifest.json`에 있다.

- 기존 120개 모두 확인. DEFAULT-02/04/10/16/18/20의 6개를 ai_refine → defer_to_spec으로 제안.
- CONFLICT-16의 무승부 예외는 ask_user → ready로 제안. 문장 자체를 바꿔 정답에 맞추지 않음.
- 구현 세부 유형 SPEC-01~20 추가. 총 140개, dev/test 각 70개. 기존 입력 유형은 보존되므로 이제 같은 유형 안에서도 정답이 다를 수 있음.
- CORE의 폭넓은 아이디어, SCOPE의 명시적 실제 연동은 ask_user 유지 제안. 데모 목적만으로 핵심 목적을 임의 선택하거나 실제 연동 요구를 숨기지 않음.
- 새 Spec 사례는 기존 도메인과 제품 조건을 재사용한 파생 사례임. 독립적인 서비스 20개가 추가된 것이 아님. 분석은 항목뿐 아니라 시나리오·도메인 단위로도 구분.
- 전체 140개 분포: ready 41, ai_refine 14, ask_user 59, defer_to_spec 26. 정확도 한 숫자만 보면 다수 라벨에 유리하므로 라벨별 성능과 분모를 함께 보고.
- 작성자가 test를 포함해 모두 재검수했으므로 숨겨진 평가셋이라고 부르지 않음. 엄밀한 최종 일반화 검증은 별도 사람이 작성한 신규 사례가 필요.

## 비용을 줄이는 실행 순서

### 1단계: 16개 소규모 판정 비교

- dev에서 네 라벨 각각 4개. 선택 ID는 manifest에 고정. 모델당 16회 × 1회, 총 32회. 첫 단계부터 전체 140개나 3회 반복은 하지 않음.
- Jev `jev-1.13.0`과 Sonnet `claude-sonnet-5-5`. 동일한 원문·고정 대상·정책·4개 기준을 전달한다. 어댑터 차이를 제외한 의미 입력을 같게 보관한다.
- 두 모델 모두 라벨만 반환. Sonnet 추출·보완·질문 작성·Jev fallback을 전부 제외. 사람 정답·이유·사례 ID·category·split은 모델 입력에서 제외.
- Sonnet thinking 설정과 출력 상한은 두 모델의 기능 차이를 고려해 실행 전에 기록한다. 비용을 줄이려고 설정을 바꾸면 이후에도 동일 조건을 유지한다. 출력이 잘리면 실패로 기록하고 정답으로 채우지 않는다.
- 무작정 여러 사례를 한 요청에 묶지 않는다. 사례 간 정보 섞임·문맥 길이 때문에 공정성이 바뀔 수 있다.
- 첫 라벨 비교는 낮은 confidence를 Sonnet으로 넘기지 않는다. 모든 valid/error 결과를 포함해 개수와 분모를 공개한다.

사전 예산 추정: Sonnet 1회 입력 2,000~4,000토큰, 출력(thinking 포함) 100~1,000토큰을 가정하면 16회 약 $0.08~$0.288. Jev 같은 입력량 16회 약 $0.00134~$0.00269. 합계 약 **$0.08~$0.30**. 실제 토큰 수를 측정한 확정 견적이나 최대 청구액이 아니다.

권장 소규모 예산은 **$0.50**. 실행 직전 요청 크기·출력 상한·재시도 조건으로 다시 견적을 내고 사용자에게 알린다. 이 문서만으로 비용 상한을 강제하지 않으며, 현재 코드에는 금액 차단 기능이 없다. 유료 실행기에 사전 견적과 누적 비용 제한을 연결한 뒤 시작한다. 계정 크레딧 잔액은 별도이며 실제 청구와 세금·환율은 확인 전이다.

단가 확인 기준: Jev 입력 $0.042/100만 토큰·출력 무료, Sonnet 5.5 입력 $2/100만·출력 $10/100만. [Jev](https://docs.typesafe.ai/models), [Claude](https://platform.claude.com/docs/en/models/overview). 실행일에 다시 확인한다.

### 2단계: 잠근 test에서 확대 비교

16개는 분기·입출력 계약과 명백한 오판을 찾는 개발용이다. 여기서 좋은 결과가 나와도 도입 확정하지 않는다. 오류 수정 후 조건을 고정하고 별도 test 70개를 두 모델 모두 같은 횟수로 실행한다. 3회 반복은 비용과 판정 흔들림을 보고 별도 결정한다. 반복 3회는 독립 사례 3배가 아니다.

### 3단계: 사용자 흐름 비교

A 기존 M1, B M2 Sonnet 단독, C M2 Jev+Sonnet 재검토를 동일 서비스 시나리오로 비교한다. 본 실험 전에 M1의 실제 커밋·모델·지원 범위·실행 가능 여부부터 확인한다. M1이 SnowChat이고 M2가 Sonnet이면 A/B 차이를 정책만의 인과 효과로 단정하지 않는다. 필요하면 같은 Sonnet에 M1/M2 정책을 적용한 별도 통제군을 두되 이를 실제 M1이라고 부르지 않는다.

B/C는 판정자 외 생성 모델·프롬프트·Review 기준을 맞춘다. 고정 답변을 주는 시뮬레이션은 비교 가능한 제어 실험이고, 실제 사용자가 답하는 실험과 별도 보고한다. 실제 사용자 비교는 순서를 교차 배치해 앞 실험의 학습 효과를 줄인다. 데모 생성까지 돌리지 않았다면 결과물 품질 향상을 주장하지 않는다.

## 성공·중단 기준 제안

### 판정 품질

- 필수 질문 회수율 = 정답 ask_user 중 예측 ask_user 비율.
- 과잉 질문률 = 정답 비-ask_user 중 예측 ask_user 비율.
- 제품 결정의 잘못된 Spec 이관 = 정답 비-defer_to_spec 중 예측 defer_to_spec 비율. 사례별 근거도 함께 점검.
- 잘못된 AI 자동처리 = 정답 ask_user 중 예측 ready/ai_refine/defer_to_spec. 명시 충돌·지원 범위 충돌을 따로 집계.
- 4분류 혼동행렬, 라벨별 recall, 모든 호출의 실패율·지연·토큰·비용. Jev confidence는 dev에서만 보정한다.

소규모 16개에서는 필수 질문 4개 중 하나라도 놓치거나 입력·응답 계약이 깨지면 원인을 먼저 검토한다. 이 작은 표본에서 Sonnet과 같다고 성능 동등성을 주장하지 않는다.

확대 비교의 도입 후보 기준: Jev가 Sonnet보다 필수 질문을 더 놓치지 않고, 명시 요구를 숨기는 자동처리·제품 결정 Spec 이관이 더 늘지 않으며, 아래 중 하나가 개선되는 경우다.

- 과잉 질문 감소; 또는
- 판정 비용 30% 이상 감소; 또는
- 판정 지연 중앙값 20% 이상 감소.

30%·20%는 검수용 제안이다. 결과를 본 뒤 유리하게 변경하지 않는다. paired 사례의 승/패와 불확실성을 함께 제시하고, 표본이 작거나 차이가 불명확하면 결론을 보류한다. Jev 자체 비교 통과는 전체 흐름 도입 승인과 다르다.

### 사용자 경험

Review까지 실제 질문 수·라운드·소요 시간, 중도 포기 수, 질문 이해도(1~5), AI 제안 수정 건수/전체 제안 수, 명시 의도 위반 사례를 비교한다. 고정 3회 제한만으로 사용자 경험 개선을 주장하지 않는다. 질문이 줄면서 의도 위반·수정 부담이 늘면 실패다.

C는 Sonnet 재검토·생성·retry까지 포함한 총비용과 총시간을 B와 비교한다. 판정이 싸도 전체가 더 느리거나 비싸면 그 사실을 밝힌다. 개선이 특정 유형에만 있으면 해당 유형에 한정한 도입을 검토한다.

## 검수 후 필요한 작업

1. 대표 경계와 정답 변경, 성공 기준에 대한 사용자 의견 반영.
2. 후보 평가셋·모델·정책·실행 조건의 해시를 잠금. 현재 기본 runner에는 수정안을 연결하지 않음.
3. 동일 조건의 Sonnet 단독 라벨 runner와 비용 사전 견적·실행 제한 구현. 현재 pipeline의 재검토+문장 생성 호출을 비교군으로 재사용하지 않음.
4. 실행 직전 예상 호출·비용 안내 후 유료 비교 실행.


## 후속 확장: 본 구현 전 프론트 구조 미리보기

사용자 요청으로 고려할 확장이다. 이번 Jev 판정 실험에는 포함하지 않으며 필수 승인 단계로 확정하지 않는다.

제안 흐름: 요구사항 Review → PRD → 화면 구조 초안·간단한 동작 미리보기 → 피드백 반영 → Spec 마무리·Task 계획 → 본 구현. 정확한 삽입 위치와 피드백 횟수는 후속 설계에서 정한다.

- 상세 디자인 없이 주요 화면, 화면 간 이동, 목록의 기본 정렬·페이지 크기, 주요 버튼 위치를 목데이터로 보여준다. 실제 백엔드 연결·완성된 서비스로 표시하지 않는다.
- 요구사항 단계에서 사소한 화면 선택을 질문으로 늘리지 않고 AI가 초안을 만들고 시각적으로 확인할 수 있게 한다. AI가 정한 기본값과 사용자 수정·확정의 출처를 보존한다.
- defer_to_spec 항목 중 화면에 드러나는 결정은 이 초안의 입력으로 전달한다. DB 인덱스·API 내부 구조처럼 사용자에게 불필요한 기술 선택은 노출하지 않는다.
- 일반 목록 정렬과 업무 배정 순서는 구분한다. 화면 피드백이 권한·승인·상태 변화 같은 제품 동작을 바꾸면 해당 요구사항과 PRD에도 반영하고, 단순 표현 변경은 화면 구조·Spec에 반영한다.
- 미리보기 피드백은 본 구현 전 검토 확장이다. 생성 완료 후 새 요구사항을 받아 고치는 기능까지 확장하지 않는다.
