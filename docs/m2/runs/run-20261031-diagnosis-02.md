# run-20261031-diagnosis-02

#10 판정과 Opus 진단을 실제 Docker와 생성 앱으로 확인한 기록이다. 2026-10-31.

## 입력과 환경

- 입력 앱: 같은 날 실제 모델로 생성한 휴가관리 앱 `run-20261031-140832`(Task 6개, 자동 점검 13개, 생성 비용 약 USD 2.89). 앱을 새로 생성하지 않고 Run 폴더를 두 벌 복사해 사용했다. 원본은 바꾸지 않았다.
- 환경: macOS, Docker Desktop 29.9.2(linux/aarch64), 이미지 `harness-sandbox:m2-1`. **WSL2에서는 실행하지 않았다.**
- 고의 실패: 연차 현황 쿼리의 조건을 `leave_type IN ('연차', '반차')`에서 `leave_type IN ('반차')`로 바꿔 커밋했다(`59d3d34`). 승인된 연차가 사용 일수에 합산되지 않는다. 사람이 넣은 결함이며 커밋 메시지에 힌트를 넣지 않았다.

## 확인한 것

- 수동 확인: 사람이 브라우저에서 실제 앱을 확인하고 원본 Run `run-20261031-140832`(`49bf68d`)에 기록했다. Spec의 26단계와 제출 항목이 일치했고 모두 `pass`다. 판정은 `passed`, AC 15개는 모두 `manual_passed`, `route`는 `none`이 되었고 모델 호출은 늘지 않았다. 복사본 `run-20261031-verify-ok`에는 제출하지 않아 `manual_pending`으로 남아 있다.
- 실제 빌드, 기동, 재시작, HTTP 점검을 거쳐 코드가 판정을 내렸고, 진단 전후로 `final_status`와 `route`(`replan_candidate`)가 그대로였다.
- 진단은 실패 점검 5개(CHK-001, 002, 006, 007, 012)를 하나의 원인으로 묶고 `GET /api/my/balance`를 지목했다. `category`는 `app_code`, `replan_scope`는 `task`였다.
- 의심 Task 첫 번째인 `TASK-002`는 해당 함수를 만든 Task와 일치한다. 재진단은 `TASK-001`, `TASK-004`도 함께 지목했다.
- 첫 검증만 자동 호출하고 재검증은 호출하지 않았다. 재검증 뒤 `stale`이면 `handoff`의 `suspected_task_ids`, `replan_scope`가 비고, `run diagnose` 뒤 다시 채워졌다.
- 바이트 기준 예약: 고의 실패 1차의 요청은 38,495바이트, 실제 입력은 19,249토큰으로 바이트 수의 약 절반이었다. 예약액 약 USD 0.47, 실제 비용 약 USD 0.11이다. 사례 1건의 값이며 상한을 보장하지 않는다.

## 실행에서 발견한 것

| 문제 | 처리 |
| --- | --- |
| `run diagnose`가 `calls[]`에는 기록하지만 `run.json`의 `cost_usd`를 갱신하지 않음 | 수정. 이 기록의 Run 폴더는 수정 전 코드로 실행되어 요약이 1.177292로 남아 있다. `calls[]` 합계는 1.288948이다 |

| `code_commit`이 커밋되지 않은 작업 트리 변경을 구분하지 못함 | 미수정. Harness의 Agent는 Task마다 커밋하므로 정상 경로에서는 생기지 않는다. 사람이 직접 고친 앱을 검증할 때는 주의가 필요하다 |
