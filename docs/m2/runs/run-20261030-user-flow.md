# 사용자 생성 흐름 실제 실행과 재개 검증 — 2026-10-30

PR #24의 `07a395b`에서 시작해, Spec 참조 규칙과 코딩 에이전트의 새 파일 생성 지침을 보완하고 같은 Run을 재개했다. 질문 정책·단일 역할 정책 변경은 포함하지 않는다. 처음부터 중단 없이 성공한 실행이 아니라 실패를 기록하고 명시적으로 재개한 결과다.

- 실제 Chromium에서 입력 → 요구사항 분석 → 검토 → 생성 버튼 한 번을 실행했다. 핵심 미결정이 없어 질문 라운드 없이 검토로 넘어갔다. 질문·답변 경로의 실제 검증은 이번 실행에 포함되지 않는다.

## 실패와 보완

1. 첫 Spec은 `IMPL-003.requirement_ids`에 `AC-001`을 넣어 거부됐다. 요구사항 참조와 점검의 AC 참조를 프롬프트에서 구분하고, 각 필드의 허용 ID와 예시를 추가했다. 검증기를 완화하거나 산출물을 수동 보정하지 않았다. 기존 PRD로 Spec을 다시 생성한 결과 계약 검증을 통과했다.
2. 첫 코딩 시도는 파일 생성 명령을 샌드박스 밖에서 실행하려다 거부됐다. Write를 명시적으로 요청했지만 에이전트는 Write 부재를 보고했다. 파일 생성도 기존 샌드박스로 수행하도록 지침을 보완했으나, 두 번째 시도의 큰 Bash 호출도 거부됐다. 두 시도 모두 파일 변경이 없어 실패로 기록했다.
3. 실제 모델 대신 localhost 가짜 API로 CLI를 검사했다. 요청한 도구 중 실제 모델 요청에는 Bash·Edit·Read만 포함됐다. 같은 권한 설정에서 짧은 샌드박스 호출로 파일을 만들 수 있었고, Edit의 `old_string=""`로 새 파일과 하위 폴더의 파일을 생성하는 것도 확인했다. 이 검사는 유료 API를 호출하지 않았다.
4. 최종 지침은 새 파일에 Edit를 사용하고, 디렉터리 생성·빌드는 각각 짧은 샌드박스 호출로 수행하도록 했다. 적용되지 않는 `Write(path)` 허용 규칙은 제거하고, 기존 `Edit(./**)` 규칙으로 쓰기 범위를 유지했다. 권한 모드와 Bash 허용 범위는 넓히지 않았다.
5. 같은 Run을 코딩부터 재개해 Task 5개가 모두 완료됐다. 완료된 PRD·Spec·Plan은 재생성하지 않았고, 이전 실패 비용과 시도 기록은 보존했다. 생성 앱의 코드는 사람이 수정하지 않았다.

`Write(path)` 대신 `Edit(path)`가 파일 쓰기를 제어한다는 기준은 [Claude Code 공식 권한 문서](https://code.claude.com/docs/en/permissions#writepath-notebookeditpath-and-globpath-rules-never-match)를 확인했다. 두 번째 실제 Bash 거부의 정확한 호출 문자열은 기존 실행 기록에 남지 않아 단정하지 않는다.

## 검증 결과

- 백엔드 오프라인 테스트 125개 통과. AC를 `requirement_ids`에 넣는 경우와 요구사항을 `ac_ids`에 넣는 경우를 각각 거부하는 테스트를 추가했다.
- Docker 빌드 성공. HTTP 점검과 컨테이너 재시작 후 지속성 점검 **11/11 통과**. `automatic_status=passed`, 내부 상태는 `manual_pending`이다.
- 실제 Harness 화면: 실패 시 사유 표시, 같은 Run 재개, 코딩 중 새로고침 복구, 완료 단계와 문구, 완료 후 새로고침 복구, 미리보기, 새 창 열기, 홈 복귀를 확인했다. 완료 후 새로고침으로 생성 요청이 추가되지 않았다.
- 생성 앱 브라우저 자동 조작: 공백 제목·빈 저자 거부, 메모 없이 추가, 최근 추가순, 검색·상태 필터·검색 결과 없음, 수정 시 공백 거부, 제목·저자·상태·메모 수정, 새로고침 및 별도 브라우저 세션에서 저장 내용 유지, 삭제 확인·취소·확정과 삭제 유지, Harness iframe 렌더링과 새 창 링크를 확인했다. 테스트용 기록은 삭제했다. 브라우저 `pageerror`는 없었다.
- 이는 실제 모델과 실제 앱을 대상으로 한 브라우저 자동 검증이다. 사람이 모든 수동 점검 항목을 확인했다고 기록하지 않았으며, `manual_pending`도 변경하지 않았다.

## 증거와 남은 한계

실행 저장소의 `prds/e0522aeac4be25b3/`에 입력 상태·검토·PRD·출처가 있고, Run 폴더에는 `run.json`, `web.json`, `artifacts/spec.rejected.json.before-reference-fix`, 최종 Spec·Plan, Task별 시도·diff, `verify.json`이 남는다. 자동 생성물과 원본 실행 기록은 Harness 저장소 밖에서 관리한다.

- 같은 입력 한 건의 재개 성공이다. 다른 입력의 안정성이나 자동 재계획·수정 루프를 검증한 결과가 아니다.
- 질문 없음 경로를 사용했으므로 질문·답변과 Open Issue 확인 경로는 기존 Mock 검증과 구분한다.
- 생성 앱의 전체 수동 점검표, 모든 데이터 삭제 후 재시딩 방지, 접근성 전체 감사는 수행하지 않았다. 테스트용 Chromium에 한글 폰트가 없어 캡처 일부는 네모로 표시됐으며, 한글 문구는 DOM으로 확인했다.
- 생성 앱 빌드 로그에는 npm 취약점 경고 2건(중간 1, 높음 1)이 남았다. 이번 자동 통과 판정은 의존성 보안 검사를 포함하지 않는다. 생성 앱 패키지를 수동 변경하지 않았다.
- 프런트 코드 변경은 없으며, 기존 TypeScript·Vite 및 Mock 화면 검증 기록은 [사용자 흐름 오프라인 검증](check-20261030-user-flow.md)에 있다.
