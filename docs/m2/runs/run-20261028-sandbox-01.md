# 실행 기록: run-20261028-sandbox-01

#9 샌드박스 실행 제한·정리·실패 기록 검증. 2026-10-28, 브랜치 `feat/m2-sandbox`.

## 입력과 환경

- 입력 앱: 사람이 직접 작성한 고정 점검용 앱. **LLM 생성물이 아니다.** 스택 계약(FastAPI + Vite React + SQLite `data/app.db`, `/api/` + `frontend/dist`)만 따르는 메모 앱이고 점검 5개(재시작 후 재실행 2개 포함, 계 7회)를 직접 정했다.
- Agent: 실제 Claude Code 대신 가짜 `claude` 스크립트. 모델 호출 없음, 비용 0.
- 환경: WSL2 Ubuntu + Docker Desktop 29.8.2, 이미지 `harness-sandbox:m2-1`(`sha256:ae43289566a8…`). WSL은 `networkingMode=mirrored`(NAT 모드에서는 WSL과 컨테이너 모두 외부 접속이 안 됐다).
- 작업 폴더: `~/harness-sandbox-check/<run_id>/app`. Harness 저장소 밖이며, 실제 실행이 쌓이는 `HARNESS_WORKSPACE_ROOT`와도 분리했다. 검증 후 삭제했다. 점검용 앱과 시나리오 드라이버는 1회성이라 저장소에 넣지 않았다.

## 진행 중 수정한 Harness 문제

- `server_log_tail`이 `docker logs`의 stdout만 받아 기동 오류(Traceback)가 빠졌다 → stderr도 함께 남기도록 수정, 테스트 추가.
- 서버 기동 대기 중 HTTP 오류 응답 객체를 닫지 않았다(ResourceWarning) → 수정.

## 한계

- 고정 점검용 앱은 생성 앱이 아니고, 가짜 `claude`는 일반적인 자식 프로세스 구조만 재현한다. 실제 생성 앱의 빌드와 실제 Claude Code의 Timeout 정리는 [run-20261028-leave-01](run-20261028-leave-01.md)에서 확인했다.
- 재시작 실패는 재시작 직전에 컨테이너를 지우는 방식으로 일부러 만들었다. 실행 실패는 다른 컨테이너가 같은 포트를 쓰게 해서 만들었다.
- HTTP 500 시나리오만 기동 대기를 90초에서 20초로 줄였다(서버가 계속 500을 응답하므로 판정은 같다).
- Test 단계는 스택 계약에 테스트가 없어 실행하지 않았다. 샌드박스는 패키지 설치를 위해 네트워크가 열려 있다.
- 오프라인 테스트: `cd backend && uv run python -m unittest discover -s tests` 96개 통과(WSL).
